# integration module (Phase 2: Bitrix intake)

Read-only intake of eligible NEW Bitrix24 deals (contract:
`docs/implementation/history/phase-2/contract.md`). No writes to Bitrix.

| File | Role |
|---|---|
| `contracts.ts` | Frozen types (lead-owned) |
| `commands.ts` | Typed wrappers for agent B's SQL commands (`integration_*`) |
| `intake-config.ts` | Parses `integration_intake_config` rows |
| `bitrix/config.ts` | `BITRIX_WEBHOOK_BASE_URL` rules: https, host = configured portal (loopback mock only with `APP_ENV=local`) |
| `bitrix/client.ts` | Allow-listed read methods, 10 s timeout, rate-limit back-off, redacted errors |
| `bitrix/events.ts` / `auth.ts` | Bounded form parse; constant-time `application_token`, portal check |
| `bitrix/receiver.ts` | `POST /api/integrations/bitrix/events` logic (record, then 200) |
| `bitrix/worker.ts` / `worker-endpoint.ts` | Bounded synchronous batch: claim -> `crm.deal.get` -> apply/fail |
| `bitrix/reconcile.ts` | Missed-event reconciliation via `crm.deal.list` |
| `server/runtime.ts` | Route wiring with the service-role client (after route auth) |
| `server/actions.ts` / `queries.ts` | Admin retry / reconcile actions; `loadIntegrationStatus`, `loadIntakeEntryRule` |
| `server/refresh-deal.ts` | Book now v2 "Refresh from Bitrix now" for one Deal (`refreshDealNow`, exported from the server-only entry `server.ts`; `index.ts` stays client-safe) |
| `won-only.ts` / `server/won-only-actions.ts` | B1.1d Won-only Deal intake: command wrappers, refusal text, Super Admin actions (entry list, prune dry run, prune) |

Scheduler: call `POST /api/integrations/bitrix/worker` with
`Authorization: Bearer $INTAKE_WORKER_SECRET` (and `?task=reconcile`
periodically). Metadata check: `scripts/bitrix-inspect-metadata.mjs`.

## Won-only Deal intake (B1.1d, 11 October 2026)

Contract `docs/implementation/frontend-first-plan-2026-10-10/b1.1/b1.1-contract-2026-10-11.md` section 3 (DEC-27), freeze note section 3.3, migration `20261119000400_b11_won_only_intake.sql`. Built and tested on disposable local databases only; not released, not used with real data.

- **Switch.** `integration_intake_config.deal_entry_stage_ids` (null = off, today's rule). The contract's `deal_intake_won_only` is `dealIntakeWonOnly` (list set). Changed only by `integration_set_deal_entry_stages(p_stage_ids, p_reason)` (Super Admin at aal2, reason 10-500, audited by the settings trigger and `integration.deal_entry_stages_set`). Never by `integration_update_sync_settings`.
- **Entry rule.** With the list set, a new Deal enters, and a removed Deal comes back, only at those stages; the list replaces the ticked stages (pipeline, sync date and owner rules stay). Refusals keep reason `not_eligible_stage`. A stored Deal keeps updating and is never removed for leaving Won.
- **Prune.** `integration_prune_deals_outside_entry_stages(p_reason, p_dry_run)`: dry run lists what would be removed and what is kept (CRM work by kind, sync waiting); it changes no Deal and writes only a record of the check (one audit row, so on the live database it needs the owner's APPROVE too). The real run soft-removes with reason `outside_entry_stage`. Deals with any CRM work (`authz.deal_crm_work`) are never removed.
- **Reversible.** A pruned Deal comes back when it reaches an entry stage. Changing or clearing the list brings back every pruned Deal in a ticked pipeline created on or after the sync date, whatever its stage (clearing = rollback; after a change, dry-run and prune again), re-checks skipped Bitrix updates and queues a full check. A pruned Deal whose pipeline was unticked meanwhile comes back when the pipeline is ticked again.
- **Settings guard.** While the list is set, `integration_update_sync_settings` refuses to untick an entry stage's pipeline (`entry_stage_pipeline_required`).
- **Full check.** The resync job lists the entry stages while the list is set, so stored Deals outside Won count as kept, not missing.
- **Owner rule.** Switching on and the real prune on the live database happen only after the owner's APPROVE, from the admin screen under a Super Admin session. Leads are untouched.

## Bitrix trip facts and all Leads (B1.2, 12 October 2026)

Freeze note `docs/implementation/frontend-first-plan-2026-10-10/b1.2/b1.2-freeze-note-part-2.md` section 4 (DEC-36, DEC-37), migration `20261120000400_b12_bitrix_trip_facts.sql`, field codes in `phase-a-bitrix-and-engines.md` section 2.0. Built and tested on disposable local databases with mock Bitrix only; not released, not used with real data. Approval drafts: `b1.2/b12-approval-drafts.md`.

- **Switches** (both off by default; `integration_set_bitrix_read_switches(p_trip_facts_read, p_lead_intake_unowned, p_reason)`, Super Admin at aal2, reason 10-500, audited by the settings trigger and `integration.bitrix_read_switches_set`; null keeps a switch). Live use needs the owner's APPROVE.
- **`bitrix_trip_facts_read`.** After the Deal/Lead apply has finished an inbox row (created, updated or confirmed unchanged), the worker sends the owner-named values (`bitrix/trip-facts.ts`: Booking Notes, Total Number of Travelers, Tour Start/End Date, Customer Type, Contact/Company links; Leads: Customer Type, links, company name) to `integration_apply_bitrix_trip_facts`, then reads only the Contact/Company the database asks for (`crm.contact.get` / `crm.company.get`, answers reduced to name, phone, e-mail at once) and stores them with `integration_apply_bitrix_party`. Only the applied Bitrix version is accepted; a party must be linked. Audit rows carry field names and issue codes, never values; the inbox stores no payload. A facts failure never fails the inbox row (counted as a provider or internal error in the run). Off: no extra read, no facts command.
- **Read helper.** `authz.bitrix_prefill_json(p_subject_kind, p_subject_id)` (granted to no API role; the calling definer command authorizes first) returns `{available, subjectKind, sourceModifiedAt, lastVerifiedAt, issues, fields: {bookingNotes, travellerTotal, tourStart, tourEnd, customerType: {enumId, code}, contact: {name, mobile, email}, company: {name, phone, email}}}`; `code` is `b2d | corporate | travel_agent` (null for an unknown option). An unusable Bitrix `DATE_MODIFY` keeps the values for the version the apply stored, with the issue `date_modify_unreadable`. `available` is false while the switch is off.
- **`lead_intake_unowned`.** In Lead scope mode, a NEW Lead whose Bitrix responsible is not an eligible pilot Sales member is stored with `owner_user_id` null ("waiting for an owner": visible to the branch Manager and the integration admin, not to Sales) instead of `ignored / owner_not_eligible`. A stored Lead that already has an owner keeps it (the event stays `ignored / owner_not_eligible`, as today); a Lead already waiting keeps following Bitrix. Linking that Bitrix user to an eligible Sales member fills the owner (`authz.reassign_bitrix_user_deals`, audit `integration.lead_owners_filled`) while the switch is on; after switching it off, Leads already waiting stay waiting (still visible to the Manager) until the switch is on again. Switching it on hands back the newest skipped `owner_not_eligible` event of each Lead (at most 2000 Leads; result and audit carry `requeued` and `notRequeued`; a full Lead check covers the rest). Owner is set in Bitrix only; the Manager cannot assign one in the CRM. Manifest mode is unchanged.
- **Always on (both switches off too).** The Lead apply records `crm_leads.source_assigned_by_id` (the Bitrix responsible) on every insert and update, so an owner can be filled later. Outcomes, reason codes and audit details are unchanged with the switches off.

## ID-proof copy to Bitrix (B1.2 DEC-43; the only Bitrix write)

Owner decision DEC-43 (target: Deal field "Aadhar and Passports", `UF_CRM_1784359513`, multiple). Migration `20261120000700_b12_id_proof_bitrix_copy.sql`; code `bitrix/id-proof-copy.ts`, wiring `server/id-proof-copy-runtime.ts` (`runIdProofCopyBatch`; scheduled by the existing Bitrix worker: after the sync work of `?task=sync` (pg_cron + pg_net, every 30 s), only while the config's switch `bitrix_id_proof_copy` is on, at most ONE job runs if at least 75 s of the 85 s invocation budget remain (60 s worst case for the copy, with bounded timeouts: reads 10 s without rate-limit retry, download 10 s, write 20 s, file check 10 s over the `urlMachine` link and same-host redirects; plus 15 s kept for the sync-stopped alert check after the answer, review E11-2). Overlapping sync runs may each run one job; the claim still gives one job per Deal at a time (E11-1). Runbook: a sync run longer than about 10 s skips the copy (`not_enough_time`), so at busy hours copies can wait several minutes; a growing queue then is expected, not a fault (E11-5); the outcome is added to the worker's answer as codes and never changes the sync's status; switch off = no extra call, same answer; no new cron entry). Built and tested with a mock portal only; switch `bitrix_id_proof_copy` off; live use needs the owner's APPROVE (draft 3 in `b1.2/b12-approval-drafts.md`).

- **Write limits.** One method (`crm.item.update` with `entityTypeId` 2, the Deal) and one field (`ufCrm_1784359513`, the item-API key of `UF_CRM_1784359513`), checked on every request body; a separate credential `BITRIX_WRITE_WEBHOOK_BASE_URL` (server env only, never logged). No record or field is ever created.
- **Append, never replace.** The field is read first through `crm.item.get` (`entityTypeId` 2, key `ufCrm_1784359513`, READ webhook; client `getDealItemField`, which keeps only that field and refuses an answer that does not show it, so a hidden field is never taken for an empty one); every file id it holds is sent back as `{id}` with exactly one new `[name, base64]` last; the reply (the whole item) must still list every prior file, and after the write the field is read again: a missing prior file stops the job (`prior_files_lost`), a new id completes it (`sent`). A 200 answer without the expected item, or for another record, is a lost answer (`unknown`, read back; review E9-1); only explicit Bitrix errors are refusals. File names are neutral (`traveller-<n>-id-<hash>.<ext>`).
- **Jobs.** One per (Deal, traveller, file sha256), enqueued by a trigger when a proof becomes stored (switch on, Bitrix-imported Deal only; an enqueue failure never blocks the upload). pending → unknown (being sent) → sent | failed; 5 attempts with back-off; a lost answer stays `unknown` and is resolved by reading the field back (never re-sent blindly); removed proofs or Deals cancel a pending job. Booking editors and the Super Admin can retry (`bitrix_id_proof_copy_retry`); `bitrix_id_proof_copy_status` shows codes per job. Audit: ids, Bitrix Deal id and the file hash; never content or file name.
- **Safety stop (review E7-1).** When any read shows that a file the field held before is gone, the worker calls `bitrix_id_proof_copy_stop`: the job fails (`prior_files_lost`), the switch goes off (settings audit, reason "automatic stop"), an alert row opens in `bitrix_id_proof_copy_stops` (Super Admin read: `bitrix_id_proof_copy_alerts`) and the batch ends. Switching on again acknowledges the alert. Jobs failed with `prior_files_lost` or `bitrix_auth_failed` are retried only by the Super Admin.
- **One Deal at a time (E7-2, E7-6).** The CRM file is downloaded and checked first, then the field is read immediately before the write. The claim is serialised, hands out at most one job per Deal and none for a Deal with another job in flight (leased, or `unknown` waiting for its read-back); the worker claims one job at a time. Run exactly one worker.
- **Recognising the copy (E7-3).** A new file id is this job's copy only when its content hash matches (read through the entry's `urlMachine` link, which carries its own token, on the portal host only, following at most 3 same-host redirects and never one to another host, refusing any text, JSON or XML answer, bounded by the expected size, in memory only, never logged; the browser link `url` needs a signed-in session and is not tried; 13 Oct 2026 live probe: `crm.deal.get` only returned browser-session links, so every read-back ended `file_facts_unavailable`) or, when Bitrix shows a size, the size and any shown name match. Otherwise the job stays `unknown` (`file_facts_unavailable` when a new file could not be read, `new_file_not_matched` when it was read and differs); never marked sent on a guess. Review E12-1: a new file that is not positively this job's never counts as "ours is absent" either (a link may answer 200 with something that is not the file), so a read-back goes back to a send (`retry`, `not_found_on_read_back`) only when the field holds no file id beyond the prior ones.
- **Undecided read-backs (E8-2).** Each `unknown` result counts (`read_back_attempts`); after 5 in a row the job ends `needs_manual_check` (not claimed again; the Deal is freed). The Super Admin sees it in `bitrix_id_proof_copy_alerts` (`manualChecks`) and alone may retry it, as a read-back.
- **Only new proofs (E7-4, E7-5).** Proofs stored before the switch goes on are not copied (owner: no backfill). The same file stored again after its job was cancelled re-arms that job.
- **Probe check.** `scripts/dev/id-proof-copy-probe-check.mjs` (lead, read webhook only, `crm.item.get`, the worker's read path): `--before` and `--after` readings of the dummy test Deal's field (ids, sizes, the status of the `urlMachine` link with the worker's redirect rule, count) and the probe (a)-(c) comparison; (d) and (e) are printed as reminders.
- **Method.** `crm.item.update`, as Bitrix's public docs recommend for file fields (lead decision 13 Oct 2026; the owner approved the field, the method is within that scope; item-API key `ufCrm_1784359513` confirmed by metadata on 13 Oct 2026); the activation approval includes one copy to a test Deal holding two dummy files whose result (files kept, new file recognised) is reported before switching on.

## Refresh from Bitrix now (Book now v2, 26 October 2026)

Build plan `docs/implementation/booking-form-v2-2026-10-26/build-plan.md` section 3 and the review round 1 rulings in `contract.md`, migration `20261129000200_bf2_bitrix_refresh.sql`. Built and tested with mock Bitrix and disposable databases only; not released, not used with real data. READ ONLY: nothing is written to Bitrix and the write credential is never used.

- **Command.** `booking_bitrix_refresh_begin(p_deal_id, p_request_id)` runs under the staff member's own session (granted to `authenticated` only): booking editor of the Deal (`authz.can_edit_booking_draft`), Deal imported from Bitrix and not removed, intake enabled and `bitrix_trip_details_read` or `bitrix_trip_facts_read` On (else `switched_off`), the scheduled sync not paused (`integration_sync_schedule.enabled`, else `sync_paused`), at most 10 refreshes per staff member per rolling minute across all Deals (`staff_limit`, `retryAfterSeconds`; table `staff_bitrix_refresh_rate`) and at most one refresh per Deal every 20 seconds by anyone (`too_soon`, `retryAfterSeconds`; table `deal_bitrix_refresh_state`). Only a refresh that passes every check counts towards the limits. It takes over a waiting (pending or failed) inbox row of the Deal or inserts one with origin `staff_refresh` (event type `RECONCILE`), leased for 90 seconds, and audits `booking.bitrix_refresh_requested` with ids only.
- **Attempts and stuck leases.** Taking over a waiting row uses one of its attempts (`attempts + 1`, as a claim does), so a failed row that is taken over is one step closer to `dead_letter`; the refresh takes over only rows below `max_attempts`. If the request never finishes its lease (server stopped, time-out), the 90-second lease expires and the scheduled batch claims the row like any other (the claim parser accepts origin `staff_refresh`); nothing else is needed to recover it.
- **Read and apply.** `refreshDealNow(staff, dealId)` (`server/refresh-deal.ts`) calls the command first; only then the privileged client runs `processInboxItem` (`bitrix/worker.ts`, the per-row code of the scheduled batch) for that row: `crm.deal.get`, then, while `bitrix_trip_facts_read` is On, the Deal's primary Contact and its Company (`crm.contact.get`, `crm.company.get`) even when the database does not ask for them, because a contact can change in Bitrix without the Deal changing. Each request has a 5-second timeout and a rate limit is not retried. An unchanged Deal (apply answer `stale_ignored`) still stores its facts.
- **Outcomes.** `updated` (the Deal, its facts or a Contact / Company changed), `unchanged`, `too_soon`, `switched_off`, `not_bitrix_deal`, `deal_removed`, `bitrix_deal_not_found`, `bitrix_unavailable` (provider, partial, not applied, not configured, unconfirmed), `not_authorized`, `environment_unset`, `invalid_input`. A provider failure fails the row with the usual back-off; a lease the request does not finish expires and the scheduled sync takes the row (its claim accepts origin `staff_refresh`). A Preview build or a missing read credential hands the row back untouched.
- **Action.** `refreshFromBitrixAction(dealId)` in `src/modules/fulfilment/server/bitrix-refresh-action.ts` returns `BookingActionResult<BitrixRefreshResult>` with plain toast text and revalidates the book route.
